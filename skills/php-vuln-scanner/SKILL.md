# PHP 依赖漏洞扫描器（php-vuln-scanner）

扫描 PHP 项目的 Composer 依赖，识别已知安全漏洞（CVE/Advisory），并给出与路由/入口的关联推断框架。

## 适用场景

适合基于 `composer.lock`、`composer.json` 或本地 advisory 规则做组件版本匹配，并需要判断受影响组件是否被项目实际使用以及是否存在可达入口。

## 不适用场景

组件版本命中规则不等于漏洞可利用。缺少准确 lock 版本、规则区间不可信、组件只是传递依赖但未加载，或没有可达入口时，应标记为待验证或组件风险。

## 核心判断

依赖扫描的结论分为三层：版本是否受影响、代码是否实际引用该组件、受影响功能是否可由项目入口触达。三层证据不能互相替代，扫描器命中只是第一层。

## 证据标准

- 可确认：准确依赖版本、可信规则、代码引用和可达触发点证据闭合，并能证明漏洞对应的安全效果。
- 待验证：版本命中但缺少代码引用、配置条件、路由映射或实际触发证据。
- 判为否：版本不在影响区间、规则不适用、组件未加载，或目标功能被禁用且无可达入口。

## 决策树

- 优先读取 `composer.lock`：确认实际安装版本和依赖关系。
- 匹配 advisory：核对包名、影响区间、修复版本和适用范围。
- 搜索代码引用：确认类、函数、配置或自动加载确实使用该组件。
- 关联路由和 sink：判断受影响功能域是否可由请求入口到达。
- 只有版本命中：输出组件风险，不直接确认应用漏洞。

## 常见误判

- 用 `composer.json` 的宽松版本约束代替 lock 中的实际版本。
- 忽略传递依赖、替换包、fork 或私有 patch。
- 假设组件已加载，却没有找到代码引用或自动发现配置。
- 将 advisory 的最大影响范围当成当前项目的真实影响。
- 自动联网、安装工具或修改依赖来补全扫描结果。

## 可用信号

项目包含 `composer.json`、`composer.lock`、`vendor/composer/installed.*`，或存在多个 Composer 子模块时，适合使用本方法。没有这些文件不代表项目不能分析，可继续从源码引用和框架配置识别组件。

## 扫描流程（按需）
> **交叉验证建议**：若项目环境中可执行 `composer audit`，建议将其输出与本 skill 的规则匹配结果交叉比对，以提升 CVE 覆盖率。`composer audit` 使用 Packagist 实时 advisory 数据库，可补充本 skill 内置规则集可能存在的时效性盲区。两者取并集作为最终漏洞清单。

1. 依赖枚举
   - 解析 composer.lock 获取 package 名称与版本
   - 处理多模块时按模块分组输出
2. 漏洞匹配
   - 针对已知 CVE 规则匹配影响版本区间
3. 触发点分析（框架）
   - 识别已知高危组件可能进入的功能域：路由入口、序列化/模板、上传/下载、鉴权链
   - 建议使用 `php-route-mapper` 输出路由后做“受影响路由推断”
4. 组件->路由关联推断（按需）
   - 可用上下文：已有 `routes_{timestamp}.md` 与 `params_{timestamp}.md` 时可直接复用；没有时从组件引用、框架配置和代码入口直接推断，不因缺少上游报告阻塞扫描
   - 证据优先级：
     1) 代码中直接引用该组件的类/函数（例如 `use Vendor\\Pkg\\{value}`、`new {value}`、`Vendor\\{value}::`）
     2) 通过模板/序列化/上传/网络相关的“已知接入点”识别该组件所在功能域（再反查路由）
     3) 仅基于命名推断属于兜底：必须标注为 `⚠️待验证`
   - 分析时关注组件的代码引用位置、实际加载方式、可达功能域和进入 Sink 的条件；无法定位的内容标记为待验证。
